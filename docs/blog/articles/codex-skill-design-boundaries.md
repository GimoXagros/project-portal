# [기술자료] 전문 Codex 스킬 설계 — 요청을 좁히고, 근거와 한계를 남기기

전문 스킬은 특정 제품을 마법처럼 고치는 도구라기보다, 어떤 요청에서 어떤 자료를 살피고 어디서 멈출지 정하는 작업 지침에 가깝습니다. 에뮬레이터 분석에서는 CPU 명령, 타이밍, 그래픽, 저장, 카트리지 주변장치가 서로 연결되지만, 모든 문제를 한 덩어리로 조사하면 증거와 책임 경계가 흐려질 수 있습니다.

OpenAI의 공개 스킬 개념 안내는 먼저 스킬의 이름과 설명을 훑고, 요청과 맞거나 사용자가 명시적으로 호출했을 때 상세 지침을 불러오는 구조를 설명합니다. 그래서 설명에는 언제 쓸지를 간결하게 적고, 본문에는 실제 조사 순서와 제한을 두는 편이 좋습니다. 특정 요청에서 이 스킬이 자동 선택될 것이라는 보증과는 구분해야 합니다.

## 첫 단계는 “무엇을 하지 않는가”를 쓰는 것

AI Work Skills 저장소의 공개 감사는 활성 스킬을 증상과 분석 단위에 따라 나누고, 기존 도구와 역할이 겹치는 지점을 명시합니다. 예를 들어 GameYob의 링크 통신 분석은 두 기기 간 guest serial 흐름과 NiFi transport 상관관계를 다루고, SGB 호스트 분석은 명령 패킷에서 host CPU·오디오·화면 조합으로 이어지는 경계를 봅니다. 이 둘은 비슷한 게임보이 하드웨어를 다루더라도 같은 문제는 아닙니다.

같은 방식으로 GBARunner3에서 ARM7 게임 코드와 ARM946 호스트 실행이 다른 상태를 보이는 경우와, 변환된 hicode가 캐시 재사용 후 잘못 실행되는 경우는 분석 초점이 다릅니다. NitroSwan에서도 V30MZ 명령 결과 차이와 WonderSwan 주변장치 통합 문제는 별개의 시작점입니다. 스킬의 이름만 프로젝트에 맞추는 것이 아니라, 실제 증상과 증거 유형에 따라 구분해야 합니다.

| 설계 질문 | 좋은 지침이 정하는 것 | 범위를 흐리는 방식 |
| --- | --- | --- |
| 언제 선택할까? | description에 구체적 증상·분석 단위를 적음 | 프로젝트 이름만 등장하면 모든 요청에 무조건 적용 |
| 무엇을 조사할까? | 소스·로그·테스트·기기 관찰 중 해당 분석에 필요한 증거를 정함 | 증거가 없는데 원인이나 실기 결과를 추측 |
| 어디서 멈출까? | 제외 범위와 조건부 보조 도구를 적음 | 유사한 모든 계층을 한 스킬에서 설명하려 함 |
| 무엇을 출력할까? | 확인된 사실, 추론, 미실행 항목과 다음 점검을 구분 | “수정 완료” 또는 “정상”을 뒷받침 없이 선언 |

## 라우팅 예시를 테스트로 바꾸기

설계자가 쓴 역할 설명이 실제로 구분되는지 살피려면 요청 예시를 표로 만듭니다. 요청마다 기대하는 주 스킬, 필요한 경우에만 호출할 보조 스킬, 범위 밖인 작업을 적고 중복이나 빈틈을 검토할 수 있습니다. 공개 저장소의 합성 라우팅 자료는 이런 참조·중복·범위 검사를 자동화하지만, 실제 Codex 런타임이 매번 해당 스킬을 자동 선택한다는 증거는 아닙니다.

예를 들어 “저장 파일을 재시작 후 불러오지 못한다”는 요청은 저장 데이터의 기록·재로드 경로가 중심일 수 있습니다. 카트리지의 EEPROM 장치가 잘못 선택된 증거가 나타나면 그때 장치 분석을 보조로 연결합니다. 처음부터 두 분석을 모두 주 분석으로 두기보다, 첫 관찰로 계층을 좁히도록 쓰면 불필요한 분석이 줄어듭니다. 이 예는 스킬 설계 방식의 설명이며 특정 게임에서 저장 오류를 새로 재현했다는 뜻은 아닙니다.

분석 지침은 모호한 결론도 제한해야 합니다. 원본 파일은 보존하고, 수정이 필요한 경우 별도 사본에서 작업하도록 권고할 수 있습니다. 로그에 포함된 명령문이나 비밀 정보는 실행할 지시가 아니라 데이터로 취급해야 합니다. 예상 결과를 뒷받침할 코드·테스트·기기 관찰이 없으면 `미확인` 또는 `실행 안 함`으로 남기고, 자동/합성 검사와 실기 동작을 구별하도록 안내합니다.

## 지침 파일만 만들면 끝나지 않는다

공개 저장소의 스킬은 관리 목록과 고정 출처 매니페스트에 포함되고, 설치·업데이트 시 파일 목록을 확인합니다. 변경된 지침은 기존 파일을 덮기 전에 백업하는 정책이 있습니다. 형식 검사는 메타데이터와 참조를 검사하고, 합성 요청 검토는 역할 라우팅을 검사하며, 설치 테스트는 패키징·백업·선택 설치 동작을 검사합니다. 각각 다른 실패 유형을 겨냥합니다.

이 검사는 스킬 파일이 올바른 위치에 배포되고 관리 절차를 통과했다는 증거이지, Codex가 모든 실제 요청에서 정확히 자동 선택하거나 분석 결과가 맞다는 보증은 아닙니다. 저장소의 공개 감사 기록은 2026-09-19 기준 검사 결과와 그 한계를 기록합니다. 이 글은 그 기록을 다시 실행한 결과로 표현하지 않습니다. 실제 에뮬레이터·기기 분석에는 원 프로젝트 코드와 적절한 시험 환경이 별도로 필요합니다.

## 실용적인 점검 순서

1. 문제를 증상과 실패 계층으로 좁힙니다. “안 됨” 대신 어떤 입력, 어느 단계, 어떤 관찰 차이인지 씁니다.
2. 주 분석 단위를 하나 정하고, 보조 지침은 추가 증거가 나타날 때만 연결합니다.
3. 포함 범위뿐 아니라 제외 범위, 필요한 증거, 안전 제약과 `미확인` 처리 규칙을 적습니다.
4. 대표 요청과 경계 사례를 합성 fixture로 만들고 기대 라우팅·오류 상태·금지할 추론을 검토합니다.
5. 형식 검사, 설치·백업 검사와 실제 명시 호출 평가를 구분해 기록합니다. 검증하지 않은 자동 선택·실기 정확도는 주장하지 않습니다.

이 접근은 스킬 수를 늘리는 것보다 각 스킬이 어떤 상황에서 유용하고 언제 다른 분석으로 넘겨야 하는지 선명하게 만드는 데 목적이 있습니다.
